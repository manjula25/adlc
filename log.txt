# review

The REVIEW phase of `docs/PROCESS.md`. Reviews the diff between `HEAD` and a fixed point along
two deliberately separate axes:

- **Standards** — does the code conform to this repo's documented coding standards?
- **Spec** — does the code faithfully implement the originating PRD / issue?

The two axes run as **parallel sub-agents** (e.g. the `reviewer` subagent) so they don't pollute
each other's context; this skill then aggregates their findings without reranking across axes.

## Process
1. **Pin the fixed point** — a commit SHA / branch / `main` / merge-base. In the autonomous loop
   this is the feature branch's base. Capture the diff once: `git diff <fixed-point>...HEAD`
   (three-dot) plus the commit list. Fail fast if the ref is bad or the diff is empty.
2. **Identify the spec source** — issue references in commit messages, the PRD from `to-prd`, or
   a spec file under `docs/`. If none exists, the Spec axis reports "no spec available".
3. **Identify the standards sources** — `CODING_STANDARDS.md`, `CONTRIBUTING.md`, ADRs, POLICY.
4. **Spawn both reviewers in parallel:**
   - **Standards** — every place the diff violates a documented standard; cite the rule;
     distinguish hard violations from judgement calls; skip anything tooling enforces.
   - **Spec** — (a) required behavior missing/partial; (b) behavior not asked for (scope creep);
     (c) requirements implemented wrongly. Quote the spec line per finding.
   - **Spawn parameter rule:** when spawning sub-agents (e.g. via `SpawnAgent`), **omit
     `agent_type`, `model`, and `reasoning_effort`** — full-history forked agents inherit these
     from the parent and the codex tool router rejects spawns that specify them. Alternatively,
     spawn without a full-history fork. Failing to follow this causes:
     `ERROR codex_core::tools::router: error=Full-history forked agents inherit the parent
     agent type, model, and reasoning effort; omit agent_type, model, and reasoning_effort,
     or spawn without a full-history fork.`
5. **Aggregate** under `## Standards` and `## Spec` headings. Do NOT merge or rerank — keeping
   the axes separate stops one from masking the other.

## Why two axes
Code can follow every standard but implement the wrong thing (Standards pass, Spec fail), or do
exactly what the issue asked while breaking conventions (Spec pass, Standards fail).

## Verdict (machine-readable — the conductor's gate reads this)
After aggregating, end with exactly one line:
```
Review verdict: APPROVE
```
or
```
Review verdict: REQUEST CHANGES — <worst finding per axis>
```
REQUEST CHANGES withholds deploy/ship; in the zero-human loop, groundable findings are fixed via
`codex-bridge`, ungroundable ones decided + logged to `ASSUMPTIONS.md`. Never pause.

## Structured output rule (required even for APPROVE)
**Always emit `## Standards` and `## Spec` sections**, even when there are no findings.  Use "No
findings." as the body when an axis is clean.  The `receiving-code-review` skill parses these
headings to build its fix list — if they are absent and the verdict is later REQUEST CHANGES, the
remediator has nothing to parse and silently no-ops.

## Hard rules for the autonomous loop

- **Never ask the user questions.** This skill runs headless — there is no human to answer.
  Asking anything kills the pipeline. If something is unclear, make the best call and note it
  in a finding.
- **Always emit exactly one `Review verdict:` line**, even if git commands fail or the diff is
  empty. If you cannot obtain a diff, emit:
  `Review verdict: REQUEST CHANGES — diff unavailable; read source files directly against spec`
  then re-attempt the review by reading the relevant source files with the file-read tool.
- **Fallback when `git diff` is unavailable:** read the source files directly (use the Read or
  Bash read tools) and compare their content against the acceptance criteria in the task.
  A missing diff is not a reason to stop — it is a reason to use a different evidence source.

# REQUIREMENTS

## Functional Requirements

1. The system shall support staff and administrator sign-in, restricted to email/password and Single Sign-On methods.
2. The system shall allow generation of invite links for onboarding new mentors, mentees, and administrators.
3. The dashboard shall display KPIs: number of active mentors, mentees, pending approvals, active matches, and unmatched mentees.
4. The system shall display recent activity, including latest submissions, approvals, and matches, with actor, action, and timestamp.
5. The system shall allow staff/admins to review and process an approval queue (pending applications).
6. The system shall support quick actions for generating invite links, reviewing approval queue, and starting new matches.
7. The system shall enable viewing, adding, and editing mentors, including name, category tags, status, capacity, profession, organization, and email.
8. The system shall enable viewing, adding, and editing mentees, with name, school, graduation year, interest tags, status, and mentor assignment.
9. The system shall allow manual addition of mentors/mentees, auto-approving them into the active pool on save.
10. The system shall provide views to manage and monitor matched, unmatched, and completed mentor-mentee relationships.
11. The system shall provide matching functionality, suggesting ranked mentors for unmatched mentees by shared categories/interests, showing % strength.
12. The system shall display full profiles for mentors/mentees, including application responses, bio, contact information, history, tags, capacity, and match history.
13. The system shall generate QR code application links for mentors and mentees, optimized for mobile, requiring no login, and render printable/downloadable QR codes.
14. New QR-based applications shall appear automatically in the approval queue for review.
15. The system shall support relationship management for matches: mark as Active, Pause, Complete; attach notes/check-ins to relationships.
16. The admin interface shall allow super admins to invite/remove other admins and manage org-wide settings.
17. Super Admins shall be able to manage category tag taxonomy used for compatibility/matching logic.
18. The system shall support configuring and customizing email notifications and templates for all relevant events (application, approval, etc.), with role-based distribution.
19. The system shall provide an editable organization profile including name, founding details, mission, statistics, and cultural context; changes are persistable.

## Data Requirements

1. The system shall persist the following entities:
    - User (fields: name, email, role, status, password hash, SSO ID, remember flag, organization)
    - Mentor (fields as above, plus: profession, organization, category tags, capacity, status, load, bio, grad year, application answers)
    - Mentee (fields similar to mentor, with school, grad year, interest tags, mentor assignment)
    - Match/Relationship (mentor, mentee, status, connected date, duration, shared tags, notes, check-ins, history, paused reason)
    - Application (type, submitted date, contact info, category tags, bio)
    - Administrator (user reference, role, permissions)
    - Category Tag (label, count/usage)
    - Organization (name, founding, mission, stats, cultural/heritage notes)
    - EmailTemplate (name, description, recipients, active flag, template content)
    - Activity Log (actor, action type, subject, timestamp)

2. QR Application links shall encode application type/form data for new mentor/mentee entries, and be uniquely identifiable for approval tracking.
3. Category tags must be many-to-many and editable, powering compatibility and matching algorithms.
4. Notes and check-ins are attached to relationship instances and maintain author, date, content fields.

## Non-Functional Requirements

1. **Authentication**: Restricted to staff and admin via password or institutional SSO; roles control access to sensitive operations.
2. **Authorization**: Only admins and above may approve/reject applications, manage users, or change organization-level settings; fine-grained role-based access control applies for each section.
3. **Security**: User credentials must be hashed in storage; QR application links must have a minimum of 128 bits entropy to prevent guessing.
4. **Performance**: All dashboard KPIs and list filters must return results in under 2 seconds for the expected data scale (up to 1,000 mentors/mentees).
5. **Data Integrity**: Manual entries must be auto-approved but tagged as such for audit purposes.
6. **Audit**: All actions (sign-ins, approvals, changes to profiles/templates/config) shall be logged with actor and timestamp for security compliance and historical traceability.
7. **Configurability**: Email templates, category tags, and org profile sections must be fully editable by super admins in the UI without requiring database or code changes.
8. **Internationalization**: System must support UTF-8 throughout to accommodate names/emails in all languages, with localizable templates (see POLICY).
9. **Frameworks**: Stack is Next.js for frontend/app and Supabase for backend/data, as per BRIEF; all requirements must be implemented using these.
